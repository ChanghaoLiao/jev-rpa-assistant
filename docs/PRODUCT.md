# 产品设计与能力边界

## 背景与目标

电商客服经常重复回答相似问题，但不同订单、产品和商家政策又不能混为一谈。
项目希望把“识别问题、选择已审核答案、执行回复、检查结果”组织成商家看得懂的桌面工作流。
让模型负责理解与选择，让程序负责页面身份、动作时序和执行证据。

## 用户路径

| 阶段 | 用户做什么 | 系统记录什么 |
|---|---|---|
| 服务接入 | 填写模型地址与密钥，保存并分别测试 | 保存、服务测试及相应验收 |
| 平台录制 | 选择账号，录制五个目标并保存 | 录制库接入与规则整理结果 |
| 界面验证 | 检查目标并验证未读变化 | 匹配、最新位置与未读验收 |
| 话术审核 | 导入、预览、审核并启用版本 | 原文、审批标记与版本索引 |
| 接待验收 | 识字核对、话术核对、真实测试发送 | 各步骤独立结果与证据 |
| 日常接待 | 明确开始，查看时间线和人工待办 | 消息来源、决策、动作与结果 |

## 关键设计取舍

- 保存设置只负责保存，不自动选图片或调用模型。
- 图片识字测试与话术选择分开，复用已保存转录，减少无意义调用。
- 最新位置由程序读取网页状态；模型不再从截图猜测是否到底。
- Jev 选择固定正文，分数保留为决策证据，不宣称是正确率。
- 左侧未读和当前会话变化共用串行处理，避免内部两条任务同时切换客户。
- 发送后通过网页新增消息核对，避免只依赖两次 OCR 完全一致。
- 开始发送尝试、调用点击、网页新增气泡确认是不同阶段。
- 客户暂停只影响该客户；定位器整体失效等全局问题仍可终止监测。

## 当前限制

源码包含闲鱼网页版＋Edge 的具体规则，不能直接视为 1688、千牛或其他平台通用适配。
网页结构、虚拟列表、浏览器权限、人工切换以及同时运行其他脚本都可能影响结果。
当前没有统一的跨进程多开锁；串行队列只约束本进程。
不包含订单系统查询能力，不证明真实收发、长时间运行或断线恢复已经稳定。

## 后续方向

1. 针对实际 1688 接待页面验证可读数据与操作方式，再编写平台适配。
2. 使用脱敏问题集评估话术覆盖和人工处理比例。
3. 完善多开互斥、连接状态和故障恢复体验，并分别验收。
4. 用长时间、跨电脑和不同缩放环境验证配置与接待稳定性。
